# Choosing a sandbox

Choose a [sandbox](../../glossary/sandbox.md) for what the code must do and what it must not reach. The size of the service does not tell you how strong the boundary needs to be. A personal project can run untrusted code, and a large service can have jobs that only read an issue.

## From requirements to a decision record

Use this method with the [Lamp decision record template](from-issue-to-patch.md#fill-in-your-decision-record).

1. **List what must work and what must stay out of reach.** Record who can supply or change the [workload](../../glossary/workload.md): source, tests, build instructions, or commands an [agent](../../glossary/agent.md) generates. List the required files, actions, and connections. Decide whether the job may share the [host](../../glossary/host.md)'s [kernel](../../glossary/kernel.md), the core of its operating system, or a kernel with other jobs.
2. **Choose an [isolation boundary](../../glossary/isolation-boundary.md) before picking a product.** A [restricted interpreter](../../glossary/restricted-interpreter.md) can give a script access to one read-only [tool](../../glossary/tool.md). The tool still checks [authorization](../../glossary/authorization.md) on each request. If a worker must run a compiler and child processes but must not use the host kernel, an [operating-system process sandbox](../../glossary/operating-system-process-sandbox.md) does not qualify. Evaluate a [virtual machine (VM)](../../glossary/virtual-machine.md) if the worker needs its own Linux kernel. Decide [where it runs and who operates it](deployment-patterns.md) separately.
3. **Choose the [isolation unit](../../glossary/isolation-unit.md): which jobs share one environment.** For example, a fresh VM for each job and a VM reused by one customer have the same kind of boundary, but different sharing rules. Record what can be kept, what must be removed, and who verifies cleanup after success, failure, and cancellation.
4. **Test the requirements before comparing cost or speed.** Use the same source revision, tests, and toolchain. Check that allowed operations succeed and forbidden ones fail for the intended reason. Compare only candidates that meet the requirements. Measure time from submission to reviewable output, including queue and setup time; record CPU, memory, disk use, cache state, and any operating cost per job. Set targets before testing. For every requirement, mark what is **documented**, **measured**, or **unknown**; an unknown requirement is not a pass. See [candidate evaluation](../../agent-sandbox-architectures.md#how-to-evaluate-a-candidate) and [Measuring a sandbox](../verification/measuring-a-sandbox.md).

## Three decisions for the same Lamp task

In all three settings, the [Lamp task](from-issue-to-patch.md) reads `LAMP-17`, fixes the wrong total in a tiny C program, compiles the fix, and tests that two items plus three items give five. The lookup script uses only a read-only issue tool in a restricted interpreter. The separate Linux worker edits a disposable [workspace](../../glossary/workspace.md) at a known revision. The worker needs no network access, issue tool, or repository [credentials](../../glossary/credential.md). The only review [artifacts](../../glossary/artifact.md) are `change.patch` and `test.log`; only authorized reviewers can read them, and they expire after seven days. The worker cannot publish. These records are proposed designs, not test results.

### Personal project on a Linux workstation

- **Required:** The developer starts the run but does not trust the agent's commands. The worker and its child processes must not read the developer's home directory or credentials, or change the original checkout. Sharing the workstation kernel is acceptable for this project.
- **Boundary and unit:** Run native tools in an operating-system process sandbox. The build and tests share one sandbox for this run only.
- **Keep and clear:** Reuse the installed read-only toolchain, not the worker or a previous build directory. Stop the process tree and remove the scratch copy and build files. Keep the two outputs in the developer's restricted review directory until expiry.
- **Why this and not the alternatives:** A plain shell provides no such file restrictions. A separate guest kernel adds setup that this project does not require.
- **Revisit when:** Outside contributors can supply builds or tests, or the workstation can no longer share its kernel with the worker.

### Internal service for several company teams

- **Required:** Team members can change builds and tests. The worker must not share the host or another job's kernel. Check the caller's team and project before an issue read, workspace attachment, or artifact read. Record who started the job, the project and revision, and the outcome. The platform team owns failed runs and cleanup.
- **Boundary and unit:** Start a fresh Linux VM per run on an internal runner. Even consecutive runs from the same team do not share a guest.
- **Keep and clear:** Reuse a read-only base image with the compiler but no team data. Destroy the guest and discard its scratch storage and build files. Keep the audit record and the two team-scoped outputs under their separate retention rules.
- **Why this and not the alternatives:** A host-kernel process sandbox fails the separate-kernel rule. A VM reused by a team would require a verified reset between runs. Start without reuse so a failed job cannot leave files for a retry.
- **Revisit when:** The service needs an internal API, starts accepting non-employee code, or misses its queue target. Check whether the problem is missing access controls or simply too few workers.

### Large service for unrelated customers

- **Required:** Any enrolled customer may supply code. A [tenant](../../glossary/tenant.md) is a customer whose data and work must stay separate. No job shares a kernel with the host or another job. Enforce tenant access separately at issue lookup, workspace attachment, and artifact retrieval. Apply [resource limits](../../glossary/resource-limit.md) and a per-tenant concurrency cap: a job above its cap waits or is rejected, while another tenant can start when capacity is available.
- **Boundary and unit:** Start a fresh Linux VM per job, assigned to one tenant. Share runner hardware only if policy permits it; never share a guest across customer jobs.
- **Keep and clear:** Reuse the read-only base image with no customer data. Do not reuse live guests or customer caches. Discard the guest and scratch storage even on cancellation. Keep the patch and test output in tenant-scoped review storage until expiry; retries get fresh storage.
- **Why this and not the alternatives:** Neither a host-kernel process sandbox nor a shared guest meets the kernel rule. One VM per tenant would separate tenants at the guest boundary, but jobs in the same tenant could still affect one another's state. A separate VM does not fix a misconfigured issue tool or storage service.
- **Revisit when:** Queue time, completion rate, or cost per job misses a target at peak load. Add capacity if runner slots are the bottleneck. Revisit the boundary or placement if the host-sharing assumption changes. Before enabling any reuse, verify what a later job can see.

Use [harmless access checks](../verification/verifying-access-rules.md) to test intended and denied paths and [tenant isolation checks](../data-and-access/multi-tenant-isolation.md) for shared services. The local checks do not establish that the VM or service enforces those rules.

## Two public flows, different requirements

[CodeRabbit Pull Request Reviews](https://docs.coderabbit.ai/overview/pull-request-review) starts with a change already proposed in a pull request (PR). [GitHub Copilot cloud agent](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-on-github) can start with a development task and propose a new PR. These are different jobs, not a benchmark or two implementations of Lamp. The comparison covers these flows only, not CodeRabbit Coding Agent, Copilot code review, or other modes. It reflects official documentation checked November 22, 2026, not product tests.

| What to check | CodeRabbit: review an existing PR | GitHub Copilot cloud agent: implement a task and propose a PR |
| --- | --- | --- |
| Input and output | Opening a PR or pushing a new commit can trigger an automatic review. CodeRabbit uses the changes and relevant repository context, with linked issues when available, and posts findings and suggestions on the existing PR. | From the Agents tab, select a repository and ask Copilot to implement a task and open a PR. [Assigning an issue](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-on-github#assigning-an-issue-to-copilot) is another entry point: Copilot receives the issue title, description, existing comments, and any extra instructions. It makes changes for a new PR and a human reviews them. |
| Tools and authority | [Analysis tools](https://docs.coderabbit.ai/tools/index) such as linters contribute findings. For example, its [ESLint integration](https://docs.coderabbit.ai/tools/eslint) permits only approved plugins. The review flow does not require a new branch, but the [GitHub App installation](https://docs.coderabbit.ai/platforms/github-com#review-permissions) requests read-and-write access to code, PRs, and checks. App permissions do not tell you what authority each analysis tool receives. | Copilot can run commands and tests on a repository copy. For a new PR, [GitHub documents](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations#copilot-cloud-agent-can-push-code-changes-to-your-repository) that a caller needs repository write access, and Copilot can push only to its assigned branch and cannot approve or merge the PR. |
| Environment and isolation | CodeRabbit [describes a cloud sandbox](https://docs.coderabbit.ai/overview/architecture) that clones the full repository for analysis. Its diagram names [Cloud Run](https://docs.cloud.google.com/run/docs/about-execution-environments), which has more than one execution environment. The sources checked do not establish which boundary applies or which runs or customers can share a live environment or physical host. | For the **Cloud** option, GitHub [documents a Linux sandbox per session](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/about-cloud-sandboxes), isolated from the user's machine and other sessions, with configurable network restrictions. That does not establish the underlying boundary technology or who can share a physical host. |
| What remains | CodeRabbit documents a reusable [cache](https://docs.coderabbit.ai/reference/caching) of source and dependencies, enabled by default, that expires within seven days. Its [FAQ](https://docs.coderabbit.ai/faq#data-security) describes separate longer-lived review context. The cache expiry does not establish a deletion deadline for all review data. | [Session data](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/session-data) documents a saved [snapshot](../../glossary/snapshot.md) of a stopped Cloud session so files and in-progress work can resume. The sources checked do not establish when every copy is deleted. PRs and commits remain separate from the worker state. |

**Scope matters.** GitHub also documents an **Actions** environment. For GitHub-hosted Actions sessions, the session environment is destroyed at the end, but the log remains. Do not transfer that cleanup rule or the characteristics of any Actions runner to the default **Cloud** option.

When you evaluate a managed service, check the documentation for the selected mode, plan, and settings. Record what can cross the boundary and what can remain after a run. If a required property is undocumented, ask the provider for evidence and verify what you can with dummy data. Do not infer a VM, a fresh environment per job, or complete deletion from the word “sandbox.”
