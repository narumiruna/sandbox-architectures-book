# Sandbox 서비스 확장하기 {#grow-a-sandbox-service}

작업이 worker를 기다린다면 처리 용량을 늘립니다. 새 사용자와 데이터가 기존 자원을 더 이상 안전하게 공유할 수 없다면 [isolation boundary](../../glossary/isolation-boundary.md)나 [authorization](../../glossary/authorization.md)을 바꿉니다. 두 결정은 별개입니다. 한 고객에게 다른 고객의 파일을 내주는 서비스는 worker를 늘려도 문제가 해결되지 않습니다.

할 일은 같습니다. [Lamp 이슈 `LAMP-17`을 조회하고, C 프로그램을 수정한 다음, 검토할 수 있도록 텍스트 패치와 테스트 로그를 반환합니다](../design/from-issue-to-patch.md). Worker는 결과를 게시할 수 없습니다. 서비스 사용자가 늘어날 때 달라지는 점은 다음과 같습니다.

| 단계 | 공유할 수 있는 것 | 사용자를 추가하기 전에 바꿔야 하는 것 |
| --- | --- | --- |
| 개인 프로젝트 | 모든 작업의 소유자는 한 개발자입니다. 작업마다 같은 읽기 전용 컴파일러 설치를 사용할 수 있지만, 수정은 각각 별도의 일회용 복사본에서 합니다. | Worker를 늘리기 전에 작업이 어디에서 대기하는지 측정합니다. 다른 사람이 코드, 테스트, 또는 지시를 제공할 수 있게 되면 경계를 다시 검토합니다. |
| 내부 서비스 | 신뢰하는 팀끼리는 서비스와 깨끗한 컴파일러 설치가 있는 읽기 전용 파일 시스템을 공유할 수 있습니다. 팀별 비공개 저장소, 빌드 결과물, 서비스 credential은 공유하지 않습니다. | 호출자를 인증하고, 작업을 해당 팀에 연결하며, 이슈, 소스, 결과물에 대한 접근 권한을 각각 확인합니다. 이 설계에서는 시도마다 새 [virtual machine (VM)](../../glossary/virtual-machine.md)을 사용합니다. |
| 고객용 서비스 | 고객마다 별도의 [tenant](../../glossary/tenant.md)로 취급합니다. 읽기 전용 기본 이미지와 검증된 공개 의존성은 공유하되, 쓰기 가능한 파일, 비공개 cache 항목, credential은 공유하지 않습니다. | 고객을 받기 전에 tenant가 올바르게 배정되고 그에 따른 제한이 적용되는지 확인합니다. 한 고객의 요청이 한꺼번에 몰려도 모든 worker 슬롯을 차지하지 못하도록 tenant별 동시 실행 한도를 설정합니다. |

## 상태와 실행 분리하기 {#separate-state-from-execution}

기존 서비스가 로컬에 있다고 가정하는 항목을 목록으로 만듭니다. 여기에는 체크아웃한 소스, 임시 파일, cache에 저장된 의존성, 이슈 조회용 credential, 저장된 패치와 로그가 포함됩니다. 이 중 worker에 필요한 항목과 worker 외부로 옮겨야 할 항목을 기록합니다. [Lamp 결정 기록](../design/from-issue-to-patch.md#fill-in-your-decision-record)을 사용해 각 항목에 소유자와 정리 규칙을 지정합니다.

| 자원 | 시범 운영에서 자원을 제어하는 주체 | 수명과 공유 방식 |
| --- | --- | --- |
| 작업 기록 | [control plane](../../glossary/control-plane.md)은 호출자를 인증하고, 소속을 확인하고, tenant를 배정하고, 작업을 대기열에 넣고, 실행 시도를 기록합니다. 제출된 프로젝트 ID나 작업 ID만으로는 소속을 확인할 수 없습니다. | 재시도할 때 작업 ID와 tenant ID는 유지하지만 새 시도 ID를 부여합니다. 상태와 소요 시간은 기록하되 credential은 기록하지 않습니다. |
| Workspace와 실행 | Control plane은 tenant의 소스에서 고정된 리비전을 선택하고 새 복사본을 worker에 연결합니다. VM과 설정된 [mount](../../glossary/mount.md)가 worker의 접근 범위를 제한합니다. | 시도마다 새 workspace를 사용합니다. 성공, 실패, 취소 어느 경우든 복사본을 삭제하기 전에 worker를 중지합니다. 정리에 실패하면 worker를 재할당하지 말고 격리한 뒤 정리를 다시 시도합니다. |
| 신원과 의존성 | 이슈 tool은 tenant를 확인하고 Lamp에 필요한 필드만 반환합니다. 시범 운영의 worker는 오프라인에서 빌드하며 [credential](../../glossary/credential.md)을 받지 않습니다. | 이슈 서비스의 credential은 모두 worker 외부에 둡니다. 깨끗한 읽기 전용 공개 입력만 공유합니다. 나중에 비공개 cache 항목을 추가하면 tenant별로 접근 권한을 확인합니다. |
| 패치와 테스트 로그 | Worker 밖의 수집기는 작업이 성공하면 예정된 두 [artifact](../../glossary/artifact.md)를 받습니다. 검토용 저장소는 가져오기 요청마다 인증된 tenant와 검토 권한을 확인합니다. | 성공한 작업의 결과물은 합의한 만료 시점까지 보관합니다. 취소하거나 실패했을 때 불완전한 결과물은 게시하거나 전송하지 않습니다. |

## 가상 tenant로 예행연습하기 {#rehearse-with-fake-tenants}

로컬 예행연습에서는 [Bubblewrap](https://github.com/containers/bubblewrap)으로 host [kernel](../../glossary/kernel.md)을 여전히 공유하는 process worker를 실행합니다. 가상 신원, 메모리 내 검토용 저장소, [검증 실습](../verification/verifying-access-rules.md)과 같은 C workload를 사용하며, 시험용 worker 슬롯은 하나가 아니라 두 개를 둡니다. 이 구성에서 실제로 어떤 workspace가 보이는지, 정리가 이루어지는지 확인합니다. Guest kernel, 신원 공급자, 영속 저장소, 운영 환경의 처리 용량은 시험하지 않습니다. 제공된 테스트 데이터만 사용합니다. 시연용 수집기는 악의적인 결과물을 처리하도록 설계되지 않았습니다.

[접근 규칙 검증하기](../verification/verifying-access-rules.md)에 나열된 Linux, Bubblewrap, Python, C 컴파일러 요구 사항을 충족합니다. 아래 명령에 필요한 [uv](https://docs.astral.sh/uv/getting-started/installation/)를 설치합니다. 저장소 루트에서 실행합니다.

```sh
uv run --offline --no-project --python /usr/bin/python3 python -B examples/rehearse_migration.py
```

1. **분리와 정리를 확인합니다.** 두 가상 tenant 모두 `LAMP-17`을 실행합니다. 각 tenant의 workspace에는 같은 경로에 서로 다른 표식이 있습니다. 각 worker에는 자기 표식만 보여야 합니다. 다른 표식은 host에서 존재를 확인하지만 worker에서는 보이지 않아야 합니다. 각 tenant는 자기 패치와 테스트 로그를 가져올 수 있어야 합니다. 다른 tenant가 작업 ID를 알아도 검토용 저장소는 접근을 거부해야 합니다. 실습에서는 worker를 하나 더 시작하고, 일부 결과물이 나타나면 취소하고, 해당 workspace가 삭제됐는지 확인한 뒤 새 workspace에서 다시 시도합니다.
2. **동일한 조건에서 처리 용량을 비교합니다.** 각 pool에 같은 작업 12개를 제출합니다. 앞선 작업이 끝날 때까지 기다리지 않고 10 ms마다 하나씩 제출합니다(초당 100건). 두 실행 모두 같은 테스트 데이터와 process 경계를 사용하고 예열 실행을 거치며, workspace나 빌드 결과물을 재사용하지 않습니다. Worker 슬롯 수만 바꿉니다. 대기열 시간은 제출한 시점부터 배정된 슬롯에서 작업이 시작되는 시점까지이며, 설정 시간은 포함하지 않습니다. p95는 95번째 백분위수의 값으로, 여기서는 12개 중 가장 오래 기다린 작업의 값입니다. 작업이 성공적으로 반환된 경우만 완료로 셉니다. 비용 모델은 측정 구간에 있는 모든 슬롯에 슬롯당 시간당 $0.06을 적용한 뒤 성공한 작업 수로 나눕니다. 실제 청구액은 아니며, 상시 유지되는 인프라, 스토리지, 트래픽은 포함하지 않습니다.
3. **전환 여부를 결정합니다.** 실습에서는 실행 전에 예시 목표를 다음과 같이 설정합니다. p95 대기열 시간은 최대 400 ms, 작업 12개는 모두 성공, 모델상 비용은 성공한 작업당 최대 $0.000020입니다. 격리나 정리에 실패하면 처리 용량을 시험하기 전에 실습을 중단합니다. 시험 환경이 목표를 놓치면 Cedar를 받지 않습니다. 두 단계의 검사를 모두 통과하면 Cedar의 새 작업은 시험 환경에서 실행하고, 기존 환경에서 이미 시작한 Lamp 작업은 그곳에서 마칠 때까지 그대로 둡니다. 실습은 신규 접수 중단 규칙도 확인합니다. 진행 중인 작업이 모두 끝난 뒤 기존 환경으로 돌아갈 수 있는 tenant는 Lamp뿐입니다.

### 결과 예시 {#example-results}

한 Linux 실행 환경(WSL2 x86-64, AMD Ryzen 9 7950X3D, kernel 6.18.33.2, Bubblewrap 0.11.1, GCC 15.2.0)에서는 Lamp와 Cedar에 각각 자기 표식만 보였으며, 둘 다 자기 패치와 로그만 가져왔습니다. 추가 작업을 취소하자 해당 workspace가 삭제됐고, 새 시도에서는 예상한 결과물이 반환됐습니다.

| Pool | 대기열 시간 중앙값 | p95 대기열 시간 | 완료 | 성공한 작업당 모델상 비용 |
| --- | ---: | ---: | ---: | ---: |
| 기존 환경, 슬롯 1개 | 358.6 ms | 710.6 ms | 12/12 | $0.00000124 |
| 시험 환경, 슬롯 2개 | 117.6 ms | 243.9 ms | 12/12 | $0.00000115 |

*이 host에서는* 슬롯을 늘리는 것만으로 대기열 목표를 달성했습니다. 그렇다고 목표 VM 구성이 검증된 것도, 기존 환경이 Cedar의 대체 환경으로 적합해진 것도 아닙니다. 고객을 받기 전에 실제로 사용할 구성에서 검사를 반복합니다.

## 새 작업을 단계적으로 전환하기 {#switch-new-jobs-in-batches}

1. 구성을 바꾸기 전에 대기 시간을 단계별로 나눕니다. Worker가 예상한 속도로 실행되는데 대기열이 길어진다면 같은 보안 policy 아래에서 슬롯을 늘려 봅니다. 반대로 환경 시작이나 빌드에 가장 오래 걸린다면 처리 용량을 늘리기 전에 [해당 단계의 시간을 측정합니다](../verification/measuring-a-sandbox.md). 새 tenant가 기존 kernel, mount, 또는 저장소 권한을 공유할 수 없다면 대기열이 비어 있어도 그 경계부터 고칩니다.
2. 실제 고객 데이터가 아니라 목표 환경에서 가상 tenant 검사와 재시도 훈련을 수행합니다. VM 설계에서는 테스트 control plane과 두 테스트 tenant 각각에 새 오프라인 VM을 마련하는 것으로 시작합니다. Host 공유가 허용되는 경우 두 VM을 같은 테스트 실행기에 배치하고 그곳에서 workspace와 결과물 경로를 확인합니다. 테스트 계정을 사용해 실제 인증 경계에서 신원이 올바르게 확인되는지, 실제 authorization 경계에서 그 신원에 올바른 접근 권한이 적용되는지 확인합니다. 시범 운영 전에 대기열 시간, 완료, 비용 목표를 합의합니다. 승인된 소수의 내부 팀부터 시작하고, 검사를 계속 통과하고 목표도 유지할 때만 단계적으로 확대합니다. 새 작업은 새 환경으로 보내고, 이미 진행 중인 작업은 시작한 환경에서 마치도록 합니다. 실행 중인 worker를 옮기거나 기존 workspace를 새 tenant에 연결하지 않습니다.
3. 접근, 정리, 또는 처리 용량 검사 중 하나라도 통과하지 못하면 신규 접수를 중단합니다. 이전 환경이 해당 작업의 현재 격리 및 authorization 요구 사항을 여전히 충족하는 경우에만 작업을 이전 환경으로 돌려보냅니다. 기존 서비스가 소유자 한 명만 지원한다면 고객 작업의 대체 환경으로 쓸 수 없습니다. 요구 사항을 충족하는 환경이 마련될 때까지 해당 작업을 보류하거나 거부합니다.
