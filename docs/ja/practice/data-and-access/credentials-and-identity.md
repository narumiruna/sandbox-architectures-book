# Credentials と実行主体の識別 {#credentials-and-identity}

ジョブに認可された操作が 1 つだけ必要なら、その操作だけを実行できるようにし、[credential](../../glossary/credential.md)（実行主体を証明したり、アクセス権を与えたりする値）は渡しません。[Lamp の実例](../design/from-issue-to-patch.md)では、host のハンドラーは、サービスの credential を必要としないローカルのテストデータを読み取ります。サービスは、スクリプトと worker の外で要求元が誰なのかを確認します。どちらのプログラムにも、要求元の credentials や、リポジトリ、issue ストレージ、レビュー用ストレージの credentials は一切渡しません。

出力の収集コンポーネントは、自身のサービス ID を使ってレビュー用ストレージに書き込みます。レビュアーは別の ID を使って、受理された出力を読み取ります。どちらの ID でも、このワークフローを通じて修正を公開することはできません。

## 別の構成：リモートの issue ストレージ {#variant-a-remote-issue-store}

後でローカルのテストデータをリモートの issue ストレージに置き換える場合、host のハンドラーを broker として使います。broker は、認可された要求を呼び出し元に代わって実行する、信頼されたコンポーネントです。ハンドラーは、スクリプトが指定したプロジェクト名ではなく、外側のサービスが確認した呼び出し元の ID を使います。ハンドラーは権限を限定した自身の credential で要求を行い、許可されたフィールドだけを返します。ハンドラーがどの issue への要求でも受け入れてしまうなら、credential を隠しても意味はありません。

ファイルや環境変数で credential を渡すと、プログラムのコードがそれをコピーできます。有効期間を短くすれば credential を使える時間は限られますが、コピーがログや保存済みの状態に残ることは防げません。この構成では credential をハンドラー内だけに保持し、どちらの runtime のファイルや環境にも置きません。

### プレースホルダーの流れをたどる {#follow-the-placeholder}

1. 架空の issue ストレージは、`<ISSUE_READ_GRANT>` で表すダミーの credential をハンドラーに渡します。ハンドラーは、スクリプトと worker の両方の境界の外にあります。この credential で許可されるのは Lamp の `LAMP-17` の読み取りだけで、発行から 5 分で失効します。Cedar の issue の読み取り、issue の変更、リポジトリへの変更の公開はできません。
2. ハンドラーは credential を使う前に、呼び出し元にその検索を許可できるかを確認します。認可されていない要求は、ストレージに問い合わせずに拒否します。ストレージは credential の権限範囲と有効期限を確認します。期限が切れるとハンドラーはその credential を破棄します。その後の検索には、改めて認可の確認を行い、新しい credential を取得する必要があります。
3. 権限範囲内の検索が有効期限内に成功し、期限切れの credential はストレージに拒否されることを確認します。ダミーの値を使い、返された issue データ、worker の設定とファイル、パッチ、テスト出力、ログ（ハンドラーのログを含む）に値が漏れていないかを確認します。保存済みの [snapshots](../../glossary/snapshot.md) も確認し、メモリが記録されていればそこも確認します。メモリの snapshot には、ファイルを削除した後もコピーが残ることがあります。worker の snapshots はジョブのデータを接続する前に取得し、ハンドラーが credentials を保持している間はハンドラーの状態を記録しないでください。

次は、[multi-tenant isolation](multi-tenant-isolation.md)で、Lamp と Cedar が互いのデータを読めないように、どこでこれらのアクセス確認を繰り返すべきかを説明します。
