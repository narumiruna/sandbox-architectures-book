# Observability とデバッグ {#observability-and-debugging}

最後に成功した手順から調べます。worker の準備が完了しなかった場合、アクセスルールで操作を拒否された場合、コンパイラが動いたもののエラーを返した場合では、対処が異なります。[Observability](../../glossary/observability.md) とは、こうした違いを見分けるために十分な証拠が得られることです。`failed` のようなステータスが 1 つあるだけでは不十分です。

[Lamp の例](../design/from-issue-to-patch.md)を使って、issue の検索から worker の準備、ビルド、クリーンアップまで、実行の流れを追います。

## 証拠を担当する層と対応づける {#match-the-evidence-to-the-layer}

[control plane](../../glossary/control-plane.md) は、実行が要求された時刻、準備が完了した時刻、停止した時刻を記録し、クリーンアップのステータスも別に記録します。[runtime](../../glossary/runtime.md) は、コマンドの結果と実行時の上限に関するイベントを報告します。tool のハンドラは issue へのアクセス可否を記録し、collector はエクスポートの成否を記録します。これらの記録は、機密情報ではない要求 ID と試行 ID で関連づけます。時系列を追うために UTC のタイムスタンプを記録し、所要時間には時刻が飛ばない時計で測った経過時間を記録します。

以下は、互いに独立した 3 つの架空の試行です。タイムスタンプとログの抜粋は、証拠の読み方を示すための例です。

| 試行とステータス（UTC） | 機密情報を除いた証拠 | 担当する層と次に確認すること |
| --- | --- | --- |
| A1: `10:00:00 provisioning` → `10:00:30 timed_out` | `workspace_attach_timeout` があり、`ready` イベントはありません。 | control plane と workspace サービス: 承認されたコピーを接続できなかった理由を調べます。途中まで割り当てられたリソースがクリーンアップされたことを確認します。 |
| A2: `10:01:00 lookup` → `10:01:01 access_denied` | issue のハンドラは、Lamp の許可範囲外を対象とした模擬要求を、レコードを読み取る前に拒否します。 | issue ハンドラの管理者: この実行の許可範囲を確認します。確認を通すためにルールを緩めてはいけません。 |
| A3: `10:02:00 ready` → `10:02:02 build_failed` | `compile_failed` で、終了ステータスは `1` です。テストは実行されていません。 | 要求元は承認されたコピーでビルドを再現し、エラーの原因を調べられます。パッチの下書きもコンパイラの生ログも保持されません。 |

操作の拒否は 1 つのイベントであり、必ずしもセッションの最終結果ではありません。その後の失敗を拒否のせいだと判断する前に、次にどのコマンドが実行されたかを確認します。[resource limit](resource-limits.md) に達した可能性がある場合は、終了コードから推測せず、上限を強制する層が明示的なイベントを報告しているかを確認します。

## 診断記録を安全に保つ {#keep-diagnostic-records-safe}

保持するのは、実行 ID と試行 ID、タイムスタンプ、段階、ステータス、理由コードなどの安全なメタデータだけです。環境のダンプ、生の引数、issue の本文、[credential](../../glossary/credential.md) の値、workspace の内容はログに記録しません。アクセスできるのは、その tenant を担当する運用者だけです。サービス運用者は、削除を確認するまでクリーンアップの記録を保持し、その後、試行の診断記録を 30 日で失効させます。`cleaned_up` イベントが確認するのは worker のクリーンアップであり、受理済みのレビュー用ファイルや診断記録の削除ではありません。

[判断記録](../design/from-issue-to-patch.md#fill-in-your-decision-record)に戻り、コピーごとに管理者と有効期限を記入します。次に[アクセスルールの検証](../verification/verifying-access-rules.md)に沿って、許可された操作は成功し、禁止された操作は想定した理由で失敗することを確かめます。
