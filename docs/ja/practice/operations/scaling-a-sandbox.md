# Sandbox サービスの規模を拡大する {#grow-a-sandbox-service}

ジョブがワーカーの空きを待っているなら、処理枠を増やします。新しい利用者やデータが加わって、これまで共有していたものを安全に共有できなくなるなら、[isolation boundary](../../glossary/isolation-boundary.md) や [authorization](../../glossary/authorization.md) を見直します。この二つは別の判断です。ある顧客に別の顧客のファイルを渡してしまうサービスは、ワーカーを増やしても直りません。

タスクは変わりません。[Lamp の issue `LAMP-17` を調べ、C プログラムを修正し、レビュー用にテキスト形式のパッチとテストログを返します](../design/from-issue-to-patch.md)。ワーカーは公開できません。サービスを利用する人が増えるにつれて変わる点は、次のとおりです。

| 段階 | 共有できるもの | 利用者を増やす前に変えるべきこと |
| --- | --- | --- |
| 個人プロジェクト | 開発者一人がすべてのジョブを所有します。ジョブは同じ読み取り専用のコンパイラ環境を利用できますが、編集には使い捨てのコピーをそれぞれ使います。 | ワーカーを増やす前に、ジョブがどこで待つかを測ります。他の人がコード、テスト、指示のいずれかを提供できるなら、境界を見直します。 |
| 社内サービス | 信頼できるチーム間でサービスと、クリーンにインストールしたコンパイラを含む読み取り専用ファイルシステムを共有できます。非公開リポジトリ、ビルドの出力、サービスの credential は共有しません。 | 呼び出し元を認証し、ジョブをそれぞれのチームに対応付け、issue、ソース、出力へのアクセスを個別に認可します。この設計では、試行ごとに新しい [virtual machine (VM)](../../glossary/virtual-machine.md) を使います。 |
| 顧客向けサービス | 顧客ごとに別の [tenant](../../glossary/tenant.md) として扱います。読み取り専用のベースイメージと検証済みの公開依存関係は共有しますが、書き込み可能なファイル、非公開のキャッシュ項目、credential は共有しません。 | 顧客の利用を許可する前に、tenant の割り当てとルールの強制が正しく機能することを確認します。一つの顧客からの要求が急増してもワーカーの全処理枠を占有できないように、tenant ごとに同時実行数の上限を設定します。 |

## 状態と実行を分離する {#separate-state-from-execution}

既存サービスが手元にあることを前提としているものを洗い出します。たとえば、チェックアウトしたソース、一時ファイル、キャッシュ済みの依存関係、issue を調べるための credential、保存済みのパッチとログです。そのうち、ワーカーに必要なものと、ワーカーの外に移すべきものを明記します。[Lamp の設計判断の記録](../design/from-issue-to-patch.md#fill-in-your-decision-record)を使い、各項目に所有者とクリーンアップのルールを割り当てます。

| リソース | 試験運用での管理主体 | 有効期間と共有範囲 |
| --- | --- | --- |
| ジョブの記録 | [control plane](../../glossary/control-plane.md) が呼び出し元を認証し、所属を確認して tenant を割り当て、ジョブをキューに入れ、試行を記録します。送信されたプロジェクト ID やジョブ ID は、所属の証明にはなりません。 | 再試行ではジョブ ID と tenant ID を引き継ぎますが、新しい試行 ID を割り当てます。状態と所要時間は記録しますが、credential は記録しません。 |
| Workspace と実行 | control plane は特定のリビジョンに固定した tenant のソースを選び、新しいコピーをワーカーに接続します。ワーカーがアクセスできる範囲は、VM とその [mount](../../glossary/mount.md) の設定で制限します。 | 試行ごとに新しい workspace を使います。成功、失敗、キャンセルのいずれの場合も、ワーカーを停止してからそのコピーを削除します。クリーンアップに失敗したら、ワーカーを再割り当てせず隔離し、クリーンアップを再試行します。 |
| ID と依存関係 | issue を扱う tool は tenant を確認し、Lamp が必要とするフィールドだけを返します。試験運用のワーカーはオフラインでビルドし、[credential](../../glossary/credential.md) は一切受け取りません。 | issue サービスの credential はすべてワーカーの外に置きます。クリーンで読み取り専用の公開入力だけを共有します。後で非公開のキャッシュ項目を追加する場合は、tenant ごとにアクセスを認可します。 |
| パッチとテストログ | 成功時に、ワーカーの外にある収集コンポーネントが、所定の二つの [artifact](../../glossary/artifact.md) を受け取ります。レビュー用ストアは、取得要求のたびに認証済みの tenant とレビュー権限を確認します。 | 成功したジョブの出力は、合意した期限まで保持します。キャンセルや失敗の場合は、不完全な出力を公開したり転送したりしません。 |

## 架空の tenant で予行演習する {#rehearse-with-fake-tenants}

ローカルでの予行演習では、process ワーカーに [Bubblewrap](https://github.com/containers/bubblewrap) を使います。このワーカーは引き続き host の [kernel](../../glossary/kernel.md) を共有します。架空の ID、インメモリのレビュー用ストア、[検証演習](../verification/verifying-access-rules.md)と同じ C workload を使い、試験用のワーカー処理枠を一つではなく二つにします。この構成で workspace の見える範囲とクリーンアップを実際に確認します。guest kernel、ID プロバイダー、永続ストア、本番環境の処理能力は検証しません。実演用の収集コンポーネントは悪意のある出力の処理を想定していないため、付属のテスト用データだけを使ってください。

[アクセスルールの検証](../verification/verifying-access-rules.md)に記載されている前提条件（Linux、Bubblewrap、Python、C コンパイラ）を満たしてください。次のコマンドを実行するために [uv](https://docs.astral.sh/uv/getting-started/installation/) をインストールしてください。リポジトリのルートから実行します。

```sh
uv run --offline --no-project --python /usr/bin/python3 python -B examples/rehearse_migration.py
```

1. **分離とクリーンアップを確認します。** 二つの架空の tenant がどちらも `LAMP-17` を実行します。各 tenant の workspace では、同じパスに異なる目印を置きます。各ワーカーからは自分の目印だけが見え、host が存在を確認した相手の目印は見えないことが必要です。各 tenant は自分のパッチとテストログを取得できる必要があります。一方、相手の tenant がジョブ ID を知っていても、レビュー用ストアはその取得要求を拒否しなければなりません。演習では、追加のワーカーを起動し、出力の一部が現れた時点でキャンセルし、workspace がなくなったことを確認して、新しい workspace で再試行します。
2. **同じ条件で処理能力を比較します。** 各プールで同じ 12 件のジョブを実行します。先行するジョブの完了を待たず、10 ms ごと（毎秒 100 件）に投入します。どちらも同じテスト用データと process 境界を使い、事前に予備実行を行います。workspace やビルドの出力は再利用しません。変えるのはワーカーの処理枠の数だけです。キュー待ち時間は、投入から、割り当てられた処理枠でセットアップ前に処理が始まるまでの時間です。p95 は 95 パーセンタイル値（ここでは 12 件のうち最も遅い値）です。正常に結果を返したジョブだけを完了として数えます。モデル上のコストは、計測期間中の全処理枠について、1 枠あたり 1 時間 $0.06 として計算し、成功したジョブ数で割ります。実際の請求額ではなく、常設のインフラ、ストレージ、通信の費用は含みません。
3. **切り替えるかどうかを判断します。** 演習では実行前に、キュー待ち時間の p95 が 400 ms 以下、12 件すべてのジョブが成功、成功 1 件あたりのモデル上のコストが $0.000020 以下という目標例を設定します。隔離またはクリーンアップが失敗した場合は、処理能力の試験に進まずに中止します。試験環境で一つでも目標に届かなければ、Cedar の利用は許可しません。両方の判定を通過した場合、Cedar の新規ジョブは試験環境で実行し、すでに旧環境で開始した Lamp のジョブはそこで完了するまで実行します。一時停止のルールも確認します。処理中のジョブをすべて完了させた後、旧環境に戻せるのは Lamp だけです。

### 結果の例 {#example-results}

ある Linux 環境（WSL2 x86-64、AMD Ryzen 9 7950X3D、kernel 6.18.33.2、Bubblewrap 0.11.1、GCC 15.2.0）で実行したところ、Lamp と Cedar にはそれぞれ自分の目印だけが見え、自分のパッチとログだけを取得できました。追加ジョブをキャンセルするとその workspace は削除され、新しい試行では期待どおりの出力が返されました。

| プール | キュー待ち時間の中央値 | キュー待ち時間の p95 | 完了数 | 成功 1 件あたりのモデル上のコスト |
| --- | ---: | ---: | ---: | ---: |
| 旧環境（1 枠） | 358.6 ms | 710.6 ms | 12/12 | $0.00000124 |
| 試験環境（2 枠） | 117.6 ms | 243.9 ms | 12/12 | $0.00000115 |

*この host では*、処理枠を増やすだけでキュー待ち時間の目標を達成できました。これは、導入先の VM 構成が要件を満たすことを保証するものではなく、旧環境を Cedar の切り戻し先にしてよいという意味でもありません。顧客の利用を受け入れる前に、実際に使う構成で同じ確認を行ってください。

## 新規ジョブを段階的に切り替える {#switch-new-jobs-in-batches}

1. 構成を変える前に、どこで時間がかかっているかを切り分けます。キューが伸びてもワーカーが想定どおりの速度で動いているなら、同じセキュリティ policy のまま処理枠を増やしてみます。環境の起動やビルドに最も時間がかかっているなら、処理枠を増やす前に[その工程を計測します](../verification/measuring-a-sandbox.md)。新しい tenant が従来の kernel、mount、ストアのアクセス権限を共有できないなら、キューが空でも先にそれらの境界を修正します。
2. 実際の顧客データではなく、導入先の環境で架空の tenant による確認と再試行の訓練を行います。VM を使う設計では、テスト用の control plane と、二つのテスト用 tenant それぞれに新しいオフライン VM を用意するところから始めます。host の共有が許可されている場合は、両 tenant の VM を同じテストランナー上で動かし、workspace と出力のパスをそこで確認します。実際に認証と authorization が行われる境界で、テストアカウントを使って ID の扱いを検証します。試験運用の前に、キュー待ち時間、完了数、コストの目標に合意します。承認済みの少数の社内チームで始め、確認項目と目標を満たし続ける場合に限って段階的に対象を広げます。新規ジョブは新しい環境に送り、実行中のジョブは開始した環境で完了させます。実行中のワーカーを移動したり、古い workspace を新しい tenant に接続したりしません。
3. アクセス、クリーンアップ、処理能力のいずれかの判定で不合格になった場合は、新規ジョブの受け入れを一時停止します。従来の環境が対象ジョブの現在の隔離要件と authorization の要件を満たす場合に限り、その環境にジョブを戻します。旧サービスが一人の所有者しかサポートしていない場合は、顧客ジョブの切り戻し先にはできません。要件を満たす環境が使えるようになるまで、それらのジョブは保留または拒否します。
