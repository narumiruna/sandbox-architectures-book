# Control plane の役割 {#control-planes}

[control plane](../../glossary/control-plane.md) は、[sandbox](../../glossary/sandbox.md) をどこで動かすか、何を渡すか、いつ削除するかを決めます。[runtime](../../glossary/runtime.md) は、[isolation boundary](../../glossary/isolation-boundary.md) の内側でコードの実行を準備し、実行します。強固な境界があっても、control plane がプロジェクトのファイルを誤った実行に接続すれば、そのプロジェクトは守れません。

[Lamp の例](../design/from-issue-to-patch.md)では、control plane が専用の Linux worker を用意し、ソースのコピーをビルドしてテストできるようにします。その後、worker とコピーを削除します。

## リクエストからクリーンアップまで {#from-request-to-cleanup}

1. **権限を確認し、policy を選びます。** control plane は、依頼者に `LAMP-17` の Lamp [session](../../glossary/sandbox-session.md) を開始する権限と、指定したソースのリビジョンを使う権限があることを確認します。それらの入力をその実行に関連付けます。control plane の [policy](../../glossary/policy.md) は、runtime、workspace サービス、収集コンポーネントの要件を定めます。要件を強制するのは各コンポーネントです。issue tool は、引き続き自分が扱うレコードへのアクセス権限を確認します。
2. **worker の配置先を決め、実行環境を用意します。** control plane は、空き容量のある [host](../../glossary/host.md) のうち、新しい [virtual machine (VM)](../../glossary/virtual-machine.md) を動かせるものを選びます。workspace サービスに承認済みの Lamp のコピーを、runtime に VM を要求します。最初のコマンドを許可する前に、報告された構成を確認します。確認項目は、正しい workspace、クリーンなイメージ、リソースの上限、外部ネットワーク接続がないことです。要件を満たせない場合は、待ち行列での期限まで待機するか、その試行を失敗として終了します。制限のゆるい構成には切り替えません。
3. **実行し、停止して、出力を収集します。** VM は、実行中のコードが使える範囲を公開されたリソースに限定します。runtime はコマンドの実行状況を報告し、control plane は worker を停止します。ビルドとテストが最後まで成功してから、収集コンポーネントが指定された 2 つのテキストファイルを受け入れられるようになります。レビュー担当者のアクセス権限は、レビュー用ストアが別に確認します。
4. **クリーンアップを確認します。** control plane は、セットアップが途中で終わった場合やエクスポートが失敗した場合も含め、どの終了経路でもリソースが削除されるまで追跡します。削除を確認できない場合は、そのリソースを使用せず、クリーンアップを再試行し、オペレーターに通知します。受け入れ済みの [artifacts](../../glossary/artifact.md) の有効期限はレビュー用ストアが管理します。worker のクリーンアップで有効期限が切れるわけではありません。

## 各コンポーネントは何を担当するか {#who-owns-what}

| コンポーネント | この例での役割 |
| --- | --- |
| Control plane | 各実行を対応する [tenant](../../glossary/tenant.md)、issue、リビジョンに関連付けます。構成を選び、準備状況、期限、クリーンアップを追跡します。 |
| インタープリターと VM runtime | インタープリターは、スクリプトが呼び出せる操作を制限します。VM runtime は、構成で指定したリソースだけを公開し、worker の状態と削除を報告します。 |
| issue tool のハンドラー | `LAMP-17` へのアクセス権限を確認し、許可されたフィールドだけを返します。 |
| workspace サービス | 承認済みの Lamp のコピーをその実行のディスクに用意し、ディスク使用量の上限を強制して、ディスクの削除を確認します。 |
| 収集コンポーネント | その実行のディスク上にある 2 つのファイルを検証し、対応するレビュー項目に書き込みます。 |
| レビュー用ストア | レビュー担当者の読み取りを毎回認可し、受け入れたファイルを有効期限に達した時点で削除します。 |
| サービスオペレーター | 環境の準備、空き容量、クリーンアップに関する障害を調査します。worker の作業用ファイルではなく、診断記録を使います。 |

ホスティング型であるこの例では、プラットフォームチームが control plane、runtime、ストレージサービスを運用します。Lamp プロジェクトのオーナーは、issue のサンプルデータを提供し、どの呼び出し元に Lamp のタスクの実行とレビューを許可するかを決めます。別の担当者が worker を運用する場合に、これらの役割がどう変わるかについては、[デプロイメントのパターン](../design/deployment-patterns.md)を参照してください。

次の [Sandbox のライフサイクル](sandbox-lifecycle.md) では、状態が変わるたびにサービスが何を残し、何を削除するかを説明します。
